# 异常与错误码设计

## 1. 响应结构

```json
{ "success": false, "data": { "retryAfter": 42 }, "code": "TOO_MANY_ATTEMPTS", "message": "尝试次数过多，请稍后再试" }
```
- `code`：稳定的大写错误码，前端按它分支处理；`message`：给用户看的中文提示；`data`：可选补充信息（不含敏感值）。
- 429 同时返回标准 `Retry-After` 头。
- 未登录（过滤器层）返回 401 `UNAUTHORIZED`，权限不足 403 `ACCESS_DENIED`，格式相同。

## 2. 产生方式

| 来源 | code | HTTP |
|---|---|---|
| 业务规则 `BusinessException(code, message[, status[, details]])` | 见下表 | 默认 400 |
| 参数校验（`@Valid`） | `VALIDATION_ERROR`（message 为「字段: 原因」） | 400 |
| JSON 解析失败 | `INVALID_REQUEST_BODY` | 400 |
| 参数类型错误 / 缺参数 | `INVALID_PARAMETER` | 400 |
| 路径不存在 / 方法不支持 / 内容类型不支持 | `NOT_FOUND` / `METHOD_NOT_ALLOWED` / `UNSUPPORTED_MEDIA_TYPE` | 404 / 405 / 415 |
| 数据库唯一键冲突 | `DUPLICATE_RESOURCE` | 409 |
| 其他数据库约束（超长、外键等） | `INVALID_DATA`（具体原因只写日志） | 400 |
| 未处理异常 | `INTERNAL_ERROR`（只写日志，不返回堆栈） | 500 |

## 4. 前端处理

| 情况 | 处理（`frontend/services/api.ts`） |
|---|---|
| 401 | 自动刷新令牌并重放一次；刷新失败清会话，跳转 `/login?next=当前路径`（登录、注册、找回密码页除外） |
| 网络不可达 / 超时 | 抛 `ApiError`，code 为 `NETWORK_ERROR` / `REQUEST_TIMEOUT`，status 为 0 |
| 业务错误 | 抛 `ApiError(message, status, code, details)`，页面显示 `message`，按 `code` 做特殊处理（如 Pro 提示、会员门槛、限流倒计时） |

## 5. 新增错误码的规则

1. 先在本文和代码里找是否已有合适的码，不要造近义词。
2. 码用大写下划线，按「对象_原因」命名；message 用中文、说清楚用户下一步该做什么。
3. 选对 HTTP 状态：参数 / 规则 400、未登录 401、无权限或需要升级 403、不存在 404、状态冲突 409、限流 429、依赖服务不可用 503。
4. 新码写进上表。
