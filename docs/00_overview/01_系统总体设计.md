# 系统总体设计

从整体看系统由哪些部分组成、怎么协作。组件细节见 [系统架构设计](../03_architecture/01_系统架构设计.md)，部署拓扑见 [部署架构设计](../03_architecture/03_部署架构设计.md)。

## 整体组成

```
用户（浏览器：桌面 / 手机）
  │
  ▼
Web（Next.js 16，frontend/）──── 页面、交互、分享图在浏览器里生成（html-to-image）
  │  /api/v1（JSON，统一信封 { success, data, code, message }）
  ▼
API（Spring Boot 4，backend/api）── 认证、业务规则、FREE/PRO 限制、归属校验、定时任务
  │                │                  │
  ▼                ▼                  ▼
MySQL 8        对象存储              外部服务
（24 张业务表）  （R2 / 本地磁盘）    Stripe · Resend/SMTP · Nominatim · Open-Meteo · 地图底图
  ▲                ▲
  │                │
视频 Worker（backend/video-worker）── 轮询数据库里的 QUEUED 任务 → Java2D 画面 + FFmpeg 合成 → 成片上传存储
```

## 核心业务链路

```
注册（邮箱验证码）→ 创建旅行 → 地点 / 行程 → 打卡（含快速打卡）→ 照片
        → 时间轴 / 地图 / 统计 / 成就（随打卡和照片实时计算）
        → 完成旅行 → 分享图 / 分享链接 / Travel Story 视频
        → （需要更多额度或高清无水印时）Trip Pro / 终身 Pro 付款
```

一致性要求：行程 → 打卡 → 时间轴 → 地图 → 统计 → 成就 必须保持一致。统计和成就不单独存「计数」，每次按打卡、照片实时计算（成就获得记录除外）。

## 主要数据流

| 数据 | 流向 |
|---|---|
| 业务数据 | 浏览器 → API → MySQL；读取时 API 聚合（时间轴、总结、回忆） |
| 照片 / 头像 / 自定义音乐 | 浏览器向 API 要预签名地址 → 直接 PUT 到存储 → 再向 API 登记元数据 |
| 分享图 | 浏览器读取数据和照片，在本地合成 PNG 后下载，不经过服务端 |
| 视频 | API 冻结分镜（`storyboard_json`）并排队 → Worker 读取分镜、照片、音乐 → 成片写入存储 → API 返回播放地址 |
| 支付 | API 创建 Stripe Checkout → 用户在 Stripe 付款 → Webhook 回到 API → 升级旅行 / 开通终身 Pro |
| 公开分享 | 访客凭 `share_token` 调公开接口，只拿到允许公开的字段（坐标默认粗化到约 1 公里） |

## 运行环境

- 本地开发：前端 3000、API 8080、MySQL 3306、开发邮件接收器 1025/1080；存储为本地磁盘，支付为 Mock。
- 生产（规划，未部署）：Railway 上的 web / api / worker / MySQL，外加 Cloudflare R2、邮件服务商、Stripe、地图底图服务商。
