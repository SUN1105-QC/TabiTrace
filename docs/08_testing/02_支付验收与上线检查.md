# 支付验收与上线检查

## 本地验证

后端：在 `backend` 运行 `mvn verify`；前端：在 `frontend` 运行 `npm run check`。

真实 MySQL 测试默认跳过。设置 `PAYMENT_TEST_DB_URL`、`PAYMENT_TEST_DB_USER`、`PAYMENT_TEST_DB_PASSWORD` 后运行：

```powershell
mvn -pl api "-Dtest=MySqlPaymentIntegrationTest" test
```

URL 指向一个可创建表的本地测试 schema。测试只使用随机 `paytest_<12位随机值>_` 前缀表；迁移和 MyBatis SQL 都重写到该前缀，结束时按依赖顺序删除自身表。不会迁移现有 Flyway schema，也不会操作现有用户数据。进程强制终止时可能遗留此前缀表，清理前须核对具体前缀。

覆盖：V1/V13/V15/V17 的支付相关结构升级到 V20、历史赠送权益识别、8 路并发下单、6 路重复回调、退款后独立购买/赠送保留、无效金额事务回滚、账号删除后的付款与事件留存、Stripe 请求位于 DB 事务外。

2026-10-28 实测：API 全量 192 项、Worker 7 项通过；补充设置页部分退款查询后，MySQL 专项 7 项全部通过。前端 61 项测试、类型检查通过，修改文件 lint 为 0 errors（存在既有警告）。隔离测试表已清理，现有 schema 的 Flyway 版本未改变。

首轮本机 Turbopack 构建在沙箱内外均因 CSS 编译子进程退出而失败。后续已将默认 `npm run build` 切换为 Webpack，`npm run check` 使用该默认路径；保留 `npm run build:turbo` 供单独排查。不把切换构建器表述为修复 Turbopack 上游问题。生产自检仍要求 `APP_URL` 等环境变量。

2026-10-29 最终复核：`mvn clean verify` 通过，API 213 项、Worker 7 项测试均无失败或跳过，API 中含真实 MySQL 专项 11 项及支付 HTTP 回调 4 项（Stripe 网络使用协议桩）。前端类型检查通过、Lint 为 0 errors / 111 warnings，7 个测试文件共 64 项通过；默认 Webpack 生产构建完成。CI 与 Compose YAML 解析通过，默认限额确认为 20 / 6000 / 3。上述为本地结果，尚未运行远程 CI、未将 V20/V21 迁移应用到现有业务库，未部署或进行真实 Stripe 收款/退款。

## Stripe Sandbox 验收

配置测试 Secret Key 与对应 Webhook Secret，Webhook 使用 snapshot 事件格式。不要在已开放公网的生产应用中切换到 mock。Webhook 订阅：

- `checkout.session.completed`
- `checkout.session.async_payment_succeeded`
- `checkout.session.async_payment_failed`
- `checkout.session.expired`
- `charge.refunded`
- `charge.dispute.created` / `charge.dispute.updated` / `charge.dispute.closed`

逐项检查单次/终身购买、取消后继续原单、关闭付款页、重复点击/多标签、网络超时后重试、漏回调后的手动及后台对账、部分/全额退款、争议胜诉/败诉。退款在 Stripe 后台操作；项目目前只同步退款结果，没有对外开放退款发起接口。

同时核对真实商户结算币种、最低收款额、费用及换汇。`STRIPE_MIN_AMOUNT` 只是本地阈值，非 Stripe 的实时报价或可收款保证。

## 状态与恢复

同一账号只有一个待付款订单。原单未关闭时不允许对其他旅行或终身方案再下单，避免多个付款页交叉扣款。

前端只按该笔订单的 `PAID` / `PARTIALLY_REFUNDED` 确认成功，不相信回跳参数。轮询结束后进入可重查的待确认状态；查询超时不会创建新订单。

渠道确认全额退款时回收该笔付款带来的权益；部分退款保留；争议暂停、胜诉恢复。已单独购买的其他权益及历史赠送保留。退款不会删除旅行/照片/视频，可能超过免费限额的既有记录保留，新增操作继续遵循现有免费限制。

V20 之前的旅行没有完整的权益来源记录。迁移对「已是 PRO、没有独立旅行付款记录」的旧旅行按保留权益处理，包括可能由旧终身套餐升级的旅行；旧终身付款退款时这些旅行需要人工核实，不能声称能够自动准确区分历史赠送与终身升级。V20 后的付款和新建旅行按付款记录精确重算。

订单先提交后请求 Stripe。创建结果未知时只复用原幂等键；超过 23 小时仍没有 Session 编号的订单停止自动创建，需要在 Stripe 后台按 metadata.payment_id 核实并恢复对应 Session，不能简单删除 PENDING 或自动新建。已有多条历史 PENDING 不合并、不凭本地时间宣布失效，应逐笔核实并关闭原渠道 Session。

## 对账配置

`PAYMENTS_RECONCILE_ENABLED` 默认 true，`PAYMENTS_RECONCILE_INTERVAL_MS` 默认 60000，`PAYMENTS_RECONCILE_BATCH_SIZE` 默认 10（上限 100）。待付款最短间隔 `PAYMENTS_RECONCILE_MIN_AGE_SECONDS` 默认 300；已结束订单最短间隔 `PAYMENTS_RECONCILE_SETTLED_AGE_SECONDS` 默认 86400。仅在 Stripe 配置完整时执行；失败记录写入尝试时间以退避，不修改成功同步时间。

## 发布边界

发布包含 API、Worker、前端和 Flyway V20–V22，不能只更新前端。正式 Secret / Webhook 配置、业务条款、退款资格及税务/收据策略仍需运营确认。用户于 2026-10-29 确认视频限额：每日 20 次 / 6000 秒、全站同时 3 个任务；代码默认已启用，未部署。购买页同步展示实际账号额度，价格与照片/打卡权益未改变。账号存储为明确标注的估算，不实施硬容量拦截；V22 补齐用户删除后的成片清理重试。详见 [成本保护与监控](../09_deployment/05_成本保护与监控.md) 和 [收费与退款运营决策草案](../02_business/05_收费与退款运营决策.md)。不要把本地自动化测试通过等同于已完成真实收款验收。
