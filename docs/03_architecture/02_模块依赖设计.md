# 模块依赖设计

依赖关系由 2026-10-14 对 `import` 语句的统计得出。新增代码要遵守「规则」；现存的环形依赖记在 [技术债](../99_management/03_已知问题与技术债.md)，不要求一次性消除，但不要再增加。

## 1. 后端（`com.tabitrace.*`）

### 分层

```
controller ──▶ service ──▶ mapper（MyBatis） ──▶ MySQL
                 │
                 ├──▶ 其他模块的 service 或 mapper（现状：直接用别的模块的 mapper 很常见，例如 TripService 用 PlaceMapper、TripPlaceMapper）
                 └──▶ common（ApiResponse、BusinessException、校验注解、ClientIp、Hashing）
security：JWT 过滤器、当前用户（SecurityUtils）
config：安全配置、生产配置校验、仅迁移模式
```

### 已存在的环形依赖（包级）

`trip ⇄ achievement`、`checkin ⇄ achievement`、`checkin ⇄ itinerary`、`checkin ⇄ photo`、`photo ⇄ achievement`、`user ⇄ auth`、`user ⇄ payment`、`user ⇄ photo`、`security ⇄ auth`。
多数是为了读取对方的实体 / 常量（例如 `PlanService` 引用 `CheckinService.FREE_CHECKIN_LIMIT`），能够启动运行，但会让模块难以单独理解和测试。

### 规则

1. `common` 不依赖任何业务模块。
2. 归属校验统一调用 `TripService.requireOwned / requireWritable`，不要在别处复制一份。
3. 存储读写只通过 `photo/storage/StorageService` 接口（local / R2 两个实现），业务代码不直接用 S3 客户端。
4. 新增跨模块调用前，先看是否会形成新的环；会的话把共享的常量或查询下沉到被依赖较少的一方。
5. Worker（`backend/video-worker`）**不依赖 API 的代码**，两者只通过数据库表 `video_projects` 和存储交换数据；表结构改动要同时检查 Worker 的 SQL。

## 2. 前端（`frontend/`）

### 分层

```
app/（页面与布局）
  └▶ components/<功能>/（业务组件）
        └▶ hooks/（页面数据）──▶ services/（API）──▶ lib/（环境、时间、站点）
        └▶ utils/（纯业务逻辑）
types/、constants/、i18n/ 被各层引用
dev/ 只能通过 lib/env.ts 的动态 import 进入（生产构建剔除）
```

### 当前依赖统计（被引用次数）

| 层 | 依赖 |
|---|---|
| components | utils 171、services 106、lib 22、hooks 12、types 18、i18n 9、constants 1 |
| hooks | services 9、components 2、lib 1、types 2、utils 2 |
| utils | services 19（几乎都是 `import type`，另有 1 处 `ApiError`）、lib 8、types 5 |
| services | utils 3、lib 2、types 2 |
| lib、types、constants | 不依赖其他层（lib 内部互相引用） |

### 规则

1. `components` 不 import `app`（现状 0 处）。
2. `utils` 只放纯函数，可以引用 services 里的**类型**，不要发请求。
3. `hooks` 引用 components 的现状只有 `useQuickCheckIn`（Context 的 hook），不要再增加。
4. 业务代码判断环境只用 `lib/env.ts`；开发数据层只能在 `isDevelopment` 分支里动态加载。
