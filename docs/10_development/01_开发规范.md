# 开发规范

从现有代码总结的**实际做法**，新代码保持一致。Git 规则见 [Git 版本管理规范](02_Git版本管理规范.md)。

## 1. 通用

- 注释、文档、提交说明、给用户看的文案用中文；标识符用英文。
- **规则只放一处**：FREE / PRO 限制、价格、视频规格是后端常量，经接口下发，前端不另写数值。
- **不编造数据**：拿不到的值显示「暂未获取」或文字封面，不借用相似图片、不回填猜测值。
- 只做最小必要修改：不改与任务无关的代码，不随意升级依赖，不随意改 Schema 或已有 API，不删除不理解的逻辑。

## 2. 命名

| 对象 | 规则 | 例子 |
|---|---|---|
| React 组件 / 文件 | PascalCase | `TripCoverImage.tsx` |
| hooks | `useXxx.ts` | `useHomeData.ts` |
| utils / lib / services 文件 | kebab-case | `share-grid.ts`、`tabitrace-api.ts` |
| 函数、变量 | camelCase | `stageTripPhoto` |
| 常量 | UPPER_SNAKE_CASE | `PHOTO_MAX_BYTES`、`FREE_CHECKIN_LIMIT` |
| Java 包 | 小写功能名 | `com.tabitrace.usermusic` |
| Java 类 | `XxxController` / `XxxService` / `XxxMapper` / `XxxEntity` / `XxxDtos` | `TripService` |
| 数据库表、列 | snake_case，表名复数 | `video_projects.render_stage` |
| 迁移文件 | `V{n}__{英文描述}.sql`，开头中文注释说明原因 | `V19__avatar_small.sql` |
| 错误码 | 大写下划线「对象_原因」 | `VIDEO_QUEUE_LIMIT` |
| localStorage 键 | `tabitrace-xxx` | `tabitrace-live-trip-id` |

## 3. 前端

- 路径别名 `@/*`；TypeScript strict。
- 所有请求经过 `services/api.ts` 的 `api()`；业务接口写在 `services/tabitrace-api.ts`（或对应的 `services/*.ts`），组件和页面不直接 `fetch` 后端。
- 页面数据放进 `hooks/useXxxData.ts`；纯逻辑放 `utils/` 并写单元测试。
- 判断环境只用 `lib/env.ts`；开发数据层只在开发分支动态加载。
- 页面宽度用 `PageContainer`；确认用 `ConfirmDialog`；会员门槛用 `MembershipGate`；Pro 限制用行内提示。
- 用户照片用 `<img>` + `srcset`，官方图用 `PlaceImage` / `hdImage()`。
- 凭证不进 localStorage。
- 没有 Prettier，不做格式化改动；ESLint 规则见 `eslint.config.mjs`（`no-floating-promises`、`no-misused-promises`、未使用变量为 error；`any` 和 React Compiler 新规则暂为 warning）。

## 4. 后端

- 按功能分包，包内 `controller / dto / entity / mapper / service`。
- Controller 只做绑定和取当前用户；规则写在 Service；写操作加 `@Transactional`。
- DTO 用 record + Jakarta Validation；坐标用 `@Latitude` / `@Longitude`。
- MyBatis 只用注解 SQL，参数一律 `#{}`。
- 统一返回 `ApiResponse<T>`；业务错误抛 `BusinessException`，新错误码按 [异常与错误码设计](../06_backend/03_异常与错误码设计.md) §5 的规则添加并登记。
- 归属校验调用 `TripService.requireOwned / requireWritable`；存储只走 `StorageService`。
- 敏感值（验证码、令牌、IP）只存哈希；日志和响应里不出现凭证。
- 现有代码里有不少写成超长单行的方法（技术债）；新代码按正常格式换行，不要顺手重排旧代码。

## 5. 数据库

- 所有结构变化走新的 Flyway 迁移；**已执行的迁移文件一个字都不能改**（包括注释）。
- 原则上只做加法；需要删除时写清原因（参考 V16）。
- 时间用 UTC（`UTC_TIMESTAMP()`）；状态列 `VARCHAR` + 默认值，合法值在代码里校验并登记到 [枚举与常量](../04_data/03_枚举与常量定义.md)。
- 改表结构时同时检查 Worker 里直接写的 SQL（`VideoJobPoller`）。

## 6. 测试

- 前端：纯逻辑写 Vitest 单测；页面行为靠 E2E。
- 后端：Service 规则写 Mockito 单测。
- 改动可在浏览器里观察的功能时，启动服务实际验证；跑 E2E 时用测试账号（`*@example.test`），结束后按 id 清理自己创建的数据。

## 7. 任务流程与完成定义

每个任务：读 `docs/README.md` → 读长期记忆 → 读相关设计与 ADR → 明确目标与验收标准 → 定位代码 → 最小修改 → 验证（typecheck / lint / test / build / 后端测试 / 必要的 E2E 或浏览器实测）→ 同步文档 → 更新长期记忆 → 必要时记 ADR / 变更。

新发现的问题先判断是否影响当前验收：是 → P0 当前处理；否 → 记入 [未完成事项](../99_management/02_未完成事项.md) 或 [技术债](../99_management/03_已知问题与技术债.md)，回到当前任务。

**完成** = 功能实现 + 实际验证通过 + 验收通过 + 相关 P0 清零 + 设计文档同步 + 长期记忆同步 + 必要的 ADR / 变更记录。

## 8. 文档同步检查（每次任务结束）

```
[ ] 需求是否变化            → 01_requirements/
[ ] 业务规则 / 状态是否变化   → 02_business/
[ ] API / 错误码是否变化     → 06_backend/02、03
[ ] 数据库 / 字段 / 枚举是否变化 → 04_data/
[ ] 权限 / 认证是否变化       → 07_security/
[ ] 页面 / 组件 / UI 规范是否变化 → 05_frontend/
[ ] 部署 / 环境变量是否变化   → 09_deployment/
[ ] 测试标准是否变化          → 08_testing/
[ ] 是否产生新的 ADR          → 99_management/04
[ ] 是否产生新的技术债 / 未完成事项 → 99_management/02、03
[ ] 长期记忆是否更新          → 99_management/01
```
只更新真正受影响的文档。
